# ADR-003 — Payment Provider Isolation: Per-Region Bulkhead in Checkout Service
**Kata:** K 4.W.5 | **Status:** Accepted | **Date:** 2026-07-31
**Deciders:** Architecture lead, Checkout engineering, Regional GMs (Marco Rossi, Junichi Tanaka)

---

## Context

Meridian operates across 22 countries with region-specific payment methods: Stripe (global card), Klarna (Nordics), Postepay / Satispay (Italy), PayPay (Japan). PSD2 SCA is mandatory on every EU card transaction (adds 500–1500ms synchronous round-trip). The checkout service must route to the correct provider per region and must not let a provider outage in one region cascade to others.

Three isolation strategies were considered:

| Option | Core idea | Key pressure point |
|---|---|---|
| A — Single payment adapter | One shared adapter routes to all providers | Provider outage or SCA failure in one region brings down checkout globally; no isolation |
| **B — Per-region bulkhead** | **Separate adapter instance per payment region; circuit breaker per provider** | **More deployment units to manage; regional routing logic in checkout service** |
| C — Third-party payment orchestration (e.g. Primer, Spreedly) | External platform handles provider routing and fallback | Adds vendor dependency; €100–300k/year licensing; 2–3 month integration time |

---

## Decision

**Option B — per-region bulkhead within the Checkout Service, with a circuit breaker per payment provider.**

The Checkout Service routes payment initiation to a per-region adapter (Stripe EU, Stripe US, Klarna, Postepay, PayPay). Each adapter runs with independent thread pool / connection pool limits (bulkhead pattern). A circuit breaker per adapter trips after 5 consecutive failures; tripped adapters return a `PAYMENT_PROVIDER_UNAVAILABLE` error to the caller — they do not wait, retry indefinitely, or block the shared checkout thread pool.

PSD2 SCA is handled within the Stripe EU adapter path only; it is not applied to non-EU regions. The SCA round-trip latency floor (500–1500ms) is accepted as a regulatory constraint, not an optimisation target.

---

## Consequences

**Positive:**
- A Klarna outage in the Nordics does not affect Stripe payments in Germany or PayPay in Japan.
- Circuit breakers prevent timeout storms from cascading through the checkout service.
- Regional GMs (Marco Rossi, Junichi Tanaka) can observe and operate their region's payment path independently via per-adapter metrics and alerts.
- No additional vendor dependency or licensing cost.

**Negative:**
- Regional routing logic in the Checkout Service must be kept current as new markets are added; stale routing config silently routes to the wrong provider.
- More Kubernetes deployment configuration to manage (one adapter deployment per region group).
- Circuit breaker thresholds (trip count, half-open window) must be tuned per provider SLA — misconfiguration can cause false trips during provider maintenance windows.

---

## Agent-Readable Summary

**Decision:** Each payment provider region has an isolated adapter with its own connection pool and circuit breaker inside the Checkout Service. A failure in one payment provider must not affect checkout flows in other regions.

**Do not** share a single payment adapter instance or connection pool across multiple payment providers or regions. Circuit breakers must be configured per provider — a shared breaker across providers would trip globally on any single provider failure, which is exactly the cascade this ADR is designed to prevent.
