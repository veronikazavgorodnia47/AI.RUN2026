# ADR-002 — POS-to-Platform Communication: GraphQL via Apollo Gateway
**Kata:** K 4.W.5 | **Status:** Accepted | **Date:** 2026-07-31
**Deciders:** Architecture lead, POS engineering, David Park (POS/ops)

---

## Context

POS Client (Electron terminal, operating on store LAN) must fetch customer identity, unified cart state, and per-SKU availability confidence in a single round-trip at checkout. Three communication approaches were considered:

| Option | Core idea | Key pressure point |
|---|---|---|
| A — Direct REST to each service | POS calls Cart Service, Identity Service, and Inventory Cache independently | 3 separate round-trips; POS must know service topology; latency compounds; brittle to service changes |
| **B — GraphQL via Apollo Gateway** | **Single POST to Apollo; resolver fan-out to downstream services** | **Gateway is a shared SPOF; requires POS to hold a service token for the gateway only** |
| C — REST aggregate endpoint (BFF) | Dedicated BFF service aggregates identity + cart + inventory for POS | Extra service to build, deploy, and operate; duplicates gateway orchestration logic |

---

## Decision

**Option B — POS communicates exclusively via Apollo GraphQL Gateway using a single query per checkout event.**

Apollo's resolver model allows the gateway to fan out to Identity Service, Cart Service, and Inventory Cache in parallel within a single client request. POS holds one machine-to-machine service token (Auth0 client credentials) scoped to the gateway only — no knowledge of downstream service topology.

The `resolveCustomerCart` query (documented in `03-integrations.md`) covers the primary POS flow. Additional POS operations (cart merge, checkout handoff) follow the same gateway-first pattern.

---

## Consequences

**Positive:**
- Single LAN round-trip from POS to gateway; downstream fan-out is network-internal.
- POS is decoupled from internal service topology — adding or splitting services does not change POS code.
- One auth surface (gateway service token) rather than per-service credentials at each POS terminal.
- Consistent with web and mobile clients — no POS-specific protocol exception to maintain.

**Negative:**
- Apollo Gateway is on the critical path for every POS operation. A gateway outage stops all in-store cart lookups. Requires gateway HA (multi-AZ EKS deployment) to satisfy David Park's "stores keep selling" constraint.
- GraphQL schema changes (field removal, type changes) must be versioned carefully — 1,400 POS terminals may run stale Electron builds that cannot be force-updated synchronously.
- LAN connectivity between POS terminal and store network edge is assumed; offline-capable POS is out of scope for Phase 1.

---

## Agent-Readable Summary

**Decision:** POS Client communicates with the platform exclusively through the Apollo GraphQL Gateway. No POS code calls internal services (Cart, Identity, Checkout) directly.

**Do not** add direct service-to-POS endpoints that bypass the Apollo Gateway. If the gateway is down, POS must fall back to degraded mode (display last-known cart, prompt associate to confirm availability manually) — it must not attempt to contact Cart Service or Identity Service directly.
