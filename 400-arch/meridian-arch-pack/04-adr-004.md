# ADR-004 — API Contract Management and Change Governance
**Kata:** K 4.W.8 (forced by adversarial pre-mortem S3-B1/B2) | **Status:** Accepted | **Date:** 2026-07-31
**Deciders:** Architecture lead, SI team leads, Lena Park (MRG internal team)

---

## Context

Three SI partners work in parallel on shared services (Cart Service, Identity Service, Checkout Service) and the Apollo GraphQL Gateway. The adversarial pre-mortem (S3-B1) identified a concrete failure mode: SI-A ships a breaking Cart Service schema change; SI-B's Gateway resolver silently returns `null` for all POS and mobile clients. This is not caught until integration testing — two weeks before Phase 1 GA — causing a programme-level slip (S3-B2).

The integration contract skeleton (`03-integrations.md`) documents the agreed API shape but does not enforce it. Breaking changes are currently only discovered in shared staging environments, which require scheduling across three SI teams and are expensive to run.

Two options were considered:

| Option | Core idea | Key pressure point |
|---|---|---|
| A — Manual API review process | Architecture lead reviews all service changes before merge | Does not scale across three SIs and six squads; review becomes a bottleneck; humans miss things under deadline pressure |
| **B — Consumer-driven contract tests in CI + change-freeze gate** | **Pact or OpenAPI diff tests run in each service's CI pipeline; architecture lead owns a 4-week change-freeze gate before each quarterly milestone** | **Requires SI teams to write and maintain contract tests; initial setup cost ~1 sprint per service** |

---

## Decision

**Option B — consumer-driven contract tests enforced in CI, with a 4-week integration change-freeze gate before each quarterly milestone.**

Every service that publishes an API consumed by Apollo Gateway (Cart Service, Identity Service, Checkout Service) must include consumer-driven contract tests (Pact or OpenAPI diff) as a required CI check. A failing contract test blocks the merge — not just the deploy.

The Apollo Gateway schema is owned by the architecture lead. No SI may ship a breaking schema change (field removal, type change, renamed field) after the change-freeze gate without written sign-off from the architecture lead. Additive changes (new fields, new optional arguments) are permitted after the gate.

---

## Consequences

**Positive:**
- Breaking changes are caught in the authoring service's own CI pipeline — before staging, before integration testing, before the change-freeze gate.
- The architecture lead's review role shifts from manual inspection to exception handling (only changes that failed contract tests and are requesting a waiver).
- The `03-integrations.md` contract skeleton becomes the source of truth for contract test generation — it is a living document, not a snapshot.

**Negative:**
- Initial setup cost: approximately one sprint per service for SI teams to instrument Pact and wire it into CI. This must be budgeted in the Phase 1 delivery plan.
- Consumer contract tests only catch the contracts they cover. If `03-integrations.md` is incomplete (missing fields, missing operations), the tests will not catch divergence on undocumented behaviour.
- The change-freeze gate adds process overhead for the three SI teams. Gate timing (4 weeks before milestone) must be communicated at programme kickoff — not discovered during delivery.

---

## Agent-Readable Summary

**Decision:** Every service API consumed by Apollo Gateway must have consumer-driven contract tests running in CI. The Apollo Gateway schema is owned by the architecture lead; breaking changes after the 4-week change-freeze gate require written sign-off.

**Do not** merge a Cart Service, Identity Service, or Checkout Service change that removes or renames an existing field without a passing contract test and architecture lead sign-off. A failing contract test is not a warning — it is a merge blocker.
